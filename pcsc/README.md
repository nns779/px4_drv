# Linux 版内蔵カードリーダー (IFD ハンドラー) 設計資料

この文書は、Linux 版の内蔵カードリーダー対応を保守する開発者に向けて、実装の目的、責務の境界、壊してはいけない条件、検証方法を記録したものです。  
利用者向けの導入手順はリポジトリルートの [README.md](../README.md#4-内蔵-b-cas-カードリーダーの利用) を参照してください。  
Windows 版の設計は [WinSCard_PX4 設計資料](../winusb/src/WinSCard_PX4/README.md) にあり、T=1 の実装はこの2つで共有しています。

## 解決する問題

px4_drv が扱う PLEX 製品と e-Better 製品の内蔵カードリーダーは、USB の CCID デバイスとして接続されていません。  
カードとの通信は、IT930x 系の USB ブリッジを介して UART と制御コマンドを送受信する構造です。  
このため、Linux 標準の pcsc-lite と `libccid` の組み合わせでは、内蔵カードリーダーを列挙できません。

Linux 版は、カーネルモジュールがカードリーダーごとに `/dev/px4card/<ID>` を作り、pcsc-lite の pcscd が読み込む IFD ハンドラー (`libifd-px4.so`) がそれを使う構成です。  
pcscd はリーダーのドライバーを差し込む仕組みを正式に持っているため、pcscd 本体やアプリケーションには手を入れずに、内蔵カードリーダーを外付けのカードリーダーと同じ一覧へ並べられます。

## 守るべき要件

変更では、次の要件を同時に満たす必要があります。

- 内蔵カードリーダーを、PC/SC 対応のアプリケーションから外付けのカードリーダーと同じ呼び出し方で使える
- 外付けのカードリーダーを `libccid` で使い続けられる
- チューナーを開いていない機器の内蔵カードリーダーも使える
- 受信に使うチューナーと、復号に使う内蔵カードリーダーが別の機器にあっても動作する
- カードとチューナーが基板の電源を共有し、最後の利用者が閉じたときだけ電源を切る
- pcscd がカードの有無を問い合わせ続けても、基板の電源が入りっぱなしにならない
- カード通信の追加や失敗が、TS 受信を止めたりドロップを発生させたりしない
- 抜去、再挿入、USB 切断、通信タイムアウトの後に、以前のカードの ATR や T=1 の連番を再利用しない
- USB 切断の後も、pcscd が開いたままの記述子がカーネルの解放済みのオブジェクトを参照しない

このうち、TS 受信を壊さないことが最優先です。

## 構成

```text
アプリケーション → libpcsclite → pcscd → libifd-px4.so (IFD ハンドラー)
                                              ↓ ioctl
                                       /dev/px4card/<ID>
                                              ↓
                       px4_card.c (機種共通層) → it930x_bcas_*() → IT930x の UART → カード
```

カーネル側は、カードの検出・電源・リセット・UART の送受信と、デバイスの寿命・排他・チューナーと共有する基板電源だけを担当します。  
ATR の解析と T=1 (再送・WTX・APDU の分割・APDU 全体の期限) は、ユーザー空間の IFD ハンドラーが担当します。

### カーネル側

ioctl のコマンドの振り分けと `it930x_bcas_*()` の呼び出しは、機種共通層の [`px4_card.c`](../driver/px4_card.c) にまとめています。  
各機種は `struct px4_card_backend` で次の4つだけを渡し、機種ごとに同じファイル操作を複製しないようにしています。

| 項目 | 内容 |
|---|---|
| `it930x` | カードの UART とカード検出の GPIO を持つ IT930x のブリッジ |
| `lock` | チューナーの制御と共有する機種のロック (カードの操作中は保持し続ける) |
| `available` | USB 切断で 0 になる機種の利用可能状態 |
| `set_power` | チューナーと共有する基板電源の、カード側の参照を取得・解放する関数 |

ロックは、`px4_card.c` 自身のロック (open・ioctl・close と登録の解除を直列化する) を先に取り、機種のロックを後に取る順序で統一しています。

### IFD ハンドラー側

[`ifdhandler.cpp`](ifdhandler.cpp) は pcsc-lite の IFD ハンドラーの関数を実装し、[`linux_card_device.cpp`](linux_card_device.cpp) は ioctl を発行する薄いアダプターです。  
T=1 の実装は、Windows 版の [`smart_card.cpp`](../winusb/src/DriverHost_PX4/smart_card.cpp) をそのままビルドして使います。

APDU の通信に失敗したときは、Windows 版と同じく T=1 のセッションだけを捨て、次の APDU の前にカードをリセットして復帰します。  
pcscd は通信の失敗でカードをリセットしないため、ここでカードを閉じると、アプリケーションが明示的にリセットするまで通信できなくなります。  
カードを閉じるのは、カードが抜かれたときと USB が切断されたときだけです。

pcscd は USB の接続を検出すると、[`Info.plist`](Info.plist) の VID と PID が一致する機器についてこの IFD ハンドラーを読み込みます。  
IFD ハンドラーは、渡された USB のバス番号とデバイス番号を sysfs の `/sys/class/px4card/<ID>` の親と照合し、その `uevent` の `DEVNAME` から開くデバイスファイルを決めます。  
同じ機種を複数台つないだときに VID と PID だけでは区別できないためです。  
USB の接続通知はカーネルがカードリーダーを登録し終える前に届くことがあるので、見つかるまで最大3秒待ちます。  
登録の直後のデバイスファイルは `root` の `0600` で、udev が `pcscd` グループの `0660` に直すまで root 以外の pcscd は開けないため、開けない (`EACCES`) 間も同じ期限まで待ちます。  
PX-Q3 系は2つの USB デバイスが同じ PID を持ち、カーネルモジュールはシリアル番号の末尾の桁が 1 の側にだけカードリーダーを登録するので、反対側は待たずにすぐ失敗させます (Windows 版の `Px4Device::HasCardReader()` と同じ判定)。  
pcscd は起動時の USB の列挙を終えてからクライアントを受け付けるため、待つと pcscd が起動するたびに最初の接続が遅れます。  
この判定を実機で確かめられているのは PX-Q3U4 だけです。

pcsc-lite は `Info.plist` の string 要素を行単位で読むため、配列の要素は1行に1つずつ書く必要があります。  
同じ行に並べると行全体が1つの値として読まれ、2つ目以降の機種が登録されません。

### デバイスファイルとリーダー名

デバイスファイルは、Windows 版のリーダー名に表示される ID を名前にして `/dev/px4card/` の下へ作ります。  
接続順や認識順で変わる番号を名前にすると、機器を抜き差ししただけで設定や試験の対象が別の機器を指してしまうためです。  
`/dev/dvb` と同じく、最後の機器を外すとカーネルが `/dev/px4card` も消すため、コンテナでは `/dev` 全体をマウントする構成を前提にしています。

ID は、USB の VID・PID・シリアル番号と、Windows 版の INF にある DeviceInterfaceGUIDs からデバイスインターフェースパスを組み立て、その小文字のパスを Windows 版と同じ 64bit FNV-1a で計算した大文字16桁の値です。  
PX-MLT5PE の例では、Windows 版の `PLEX PX-MLT5PE Smart Card Reader (ID: E0044EBBED627D79)` に対して、Linux 版のデバイスファイルは `/dev/px4card/E0044EBBED627D79` になります。  
PX-MLT5U は未発売の機種で、公式の Windows 用ドライバーに定義があるため対応していますが、Windows 版の INF はありません。  
このため、パス末尾の `#{guid}` を省いて ID を計算します。  
発売されて INF を用意したときは、その GUID を `px4_card.c` の表へ加えます (それまで使われている機器はないので、ID が変わって困る利用者はいません)。

シリアル番号が無い、空、255バイトを超える、`.` または `..` である、または ASCII の英数字・`.`・`-`・`_` 以外の文字を含む場合は、`usb-<USB の接続位置>` (例: `usb-1-3`) を代わりに使います。  
同じ名前が既に使われている場合は、後から登録する側の末尾へ `-1` 、`-2` のように空いている番号を付けます。  
カードリーダーは px4_drv が登録する `px4card` クラスのデバイスで、sysfs では `/sys/class/px4card/<ID>` 、udev の規則では `SUBSYSTEM=="px4card"` として現れます。  
汎用の misc クラスを使うとクラスの中に `px4card` の階層を作れず、sysfs の名前とデバイスファイルの名前が食い違うため、専用のクラスにしています。

デバイスファイルの権限は `pcscd` グループの `0660` です。  
デバイスファイルを開くのは pcscd だけで、pcsc-lite 2.4 以降は systemd の下の pcscd が `pcscd` ユーザーで動くため、libccid の規則と同じくこのグループに読み書きを許可しています。  
`pcscd` グループのない古い環境では udev がグループの指定を無視し、root で動く pcscd が開きます。

誰でも開ける `0666` にしなかったのは、ほかのユーザーがデバイスファイルを開いたままにすると、1つのプロセスしか開けない作りのために pcscd が開けなくなり、録画の復号が止まるためです。  
開けなかったときは、IFD ハンドラーが失敗したパスと errno を pcscd のログへ出します。

pcscd に表示されるリーダー名は、次のようにデバイスファイル名と同じ ID を含みます。

```text
PLEX PX-MLT5PE Smart Card Reader [ID: E0044EBBED627D79] (000042546005001) 00 00
```

pcscd は、`Info.plist` の名前、`[USB のインターフェース名]` 、`(USB のシリアル番号)` 、pcscd 自身の番号をつなげてリーダー名を作ります。  
IFD ハンドラーの API にはリーダー名を返す手段がなく、名前は pcscd が IFD ハンドラーを開く前に決めます。  
そこで、px4_drv はインターフェース名を持たない機器について、USB インターフェースの sysfs の `interface` 属性を自分で作り、`ID: <ID>` を返すようにしています。  
pcscd はこの属性をインターフェース名として読むので、リーダー名に `[ID: ...]` が入ります。

pcscd は USB が追加されたという通知を受けて名前を作るため、属性は probe の中で、ファームウェアの読み込みなど時間のかかる初期化より先に作っています。  
ドライバーを外したときに属性が残ると、解放したモジュールの関数を指したままになるので、disconnect と probe の失敗の経路で必ず消します。  
括弧の中のシリアル番号と末尾の番号は pcscd が付けるもので、外すことはできません。

ただし、px4_drv のモジュールを読み込む前に pcscd が USB を列挙した場合は、名前を作る時点に属性がまだないため、リーダー名に `[ID: ...]` が入りません。  
カーネルは USB の追加を通知してからドライバーの probe を呼ぶので、カーネル側ではこの順序を防げません。  
通常の起動では udev がモジュールを読み込んでから pcscd が起動し、抜き差しでもモジュールは読み込み済みなので、起きるのは手作業でモジュールを読み込み直した場合などに限られます。  
pcscd を起動し直すと、ID の入った名前になります。

同じ VID・PID・GUID・シリアル番号を持つ機器の ID は同じになり、Linux 版では2台目以降のデバイスファイル名へ `-1` などを付けて区別します。  
このとき、リーダー名の `[ID: ...]` はどちらも同じ値になります。

## ioctl の仕様

定義は [`include/px4_card_ioctl.h`](../include/px4_card_ioctl.h) にあります。  
各コマンドは Windows 版の `CardDevice` ([`card_device.hpp`](../winusb/src/DriverHost_PX4/card_device.hpp)) の関数と1対1に対応し、引数はそのコマンドに必要な型だけを受け渡します。  
マジック番号と書き方は、チューナーの ioctl ([`include/ptx_ioctl.h`](../include/ptx_ioctl.h)) と同じ 0x8d です。

| コマンド | 引数 | 内容 |
|---|---|---|
| `PX4_CARD_POWER_ON` | なし | 基板電源の参照を取って UART を初期化する (電源投入済みなら何もしない) |
| `PX4_CARD_POWER_OFF` | なし | 基板電源の参照を解放する (デバイスファイルを閉じたときも同じ処理を行う) |
| `PX4_CARD_DETECT` | `__u32` (出力) | カードがあれば 1 、なければ 0 を返す (電源を入れていなくても使える) |
| `PX4_CARD_RESET` | なし | カードをリセットし、UART を ATR の受信速度 (9600bps) へ戻す |
| `PX4_CARD_SET_BAUDRATE` | `__u32` (入力) | UART の速度を bps で渡す (9600 、19200 、38400 のいずれか) |
| `PX4_CARD_RX_READY` | `__u32` (出力) | カードの応答を受信し終えていれば 1 、まだなら 0 を返す |
| `PX4_CARD_READ` | `struct px4_card_frame` (入出力) | `length` に `data` の容量を渡し、実際の受信長とデータが返る |
| `PX4_CARD_WRITE` | `struct px4_card_frame` (入力) | `data` の先頭から `length` バイトを1つの UART フレームとして送信する |

`struct px4_card_frame` は `__u8 length` と `__u8 data[255]` だけの 256 バイトで、32bit と 64bit のどちらのユーザー空間でも同じ配置になり、詰め物 (パディング) もありません。  
`READ` と `WRITE` の `length` は1以上で、0 は `EINVAL` になります。  
電源を入れていない状態で UART を操作するコマンドは `EHOSTDOWN` を、USB 切断後のコマンドは `ENODEV` を返します。

カーネルモジュール (DKMS) と IFD ハンドラー (deb) は別々に更新されるので、公開したコマンドの番号・引数・意味は変えず、機能は新しい番号のコマンドとして追加します。  
古いカーネルモジュールは知らない番号に `ENOTTY` を返し、IFD ハンドラーはそのことを pcscd のログに残します。  
番号が変わらない限り意味も変わらないので、ABI のバージョン番号や予約フィールド (reserved) は持たせていません。

## 基板電源の取り決め

カードはチューナーと同じ基板電源の利用者として数え、最後の利用者が閉じたときだけ電源を切ります。

- カードを開いたままチューナーを閉じても電源は切らず、チューナーが受信中にカードを閉じても切らない
- チューナーを開くときにカードが電源を使っていれば、電源は入れ直さずに受信回路の初期化だけを行う
- 停止の要求は、ハードウェア操作の成否にかかわらず停止済みとして記録し、投入は成功したときだけ記録する
- PX4 系の2基連動モデルでは、`px4_mldev` が Windows 版の `MultiDevice::SetCardPower()` と同じく、カードの参照も含めて両方の基板の電源を決める

カードの検出 (`PX4_CARD_DETECT`) は電源を入れずに行います。  
pcscd はカードの有無を定期的に問い合わせ続けるため、検出だけで電源の参照を取ると、何も受信していなくても基板の電源が切れなくなるためです。  
GPIO H6 の入力設定は通常 `it930x_bcas_init()` で行いますが、電源を入れる前の検出に備えて検出のたびに設定し直します (2回目以降は GPIO のキャッシュで USB 転送を省きます)。

## カードの共有と排他制御

`/dev/px4card/` の下のデバイスファイルは1つのプロセスしか開けず、2つ目の open は `EBUSY` になります。  
T=1 の連番と再送の状態は1つのセッションだけが持てるため、複数のアプリケーションからの共有と排他は pcscd が受け持ちます。  
open しただけでは電源を入れず、最後の記述子を閉じたときにカードの電源の参照も解放します。

## ATR と T=1

ATR の解析、通信速度の選択、T=1 の状態機械は Windows 版と共有する `smart_card.cpp` が担当し、ACAS を含む取り決めは [WinSCard_PX4 設計資料](../winusb/src/WinSCard_PX4/README.md#atr-と-t1) に従います。  
状態遷移の試験 (`smart_card_state_test.cpp`) も共有しているため、T=1 の修正は Windows 版と Linux 版の両方へ同時に反映されます。

## タイムアウト

APDU 全体の絶対期限は、Windows 版と同じく `smart_card.cpp` が操作の合間に検査するので、ioctl の引数は期限を持っていません。  
1回の ioctl は、既存の USB 制御転送のタイムアウト (モジュールのパラメーター `ctrl_timeout` で、初期値は 3000ms) で打ち切られます。  
T=1 の待機をカーネルへ置くと、TS 受信と共有する機種のロックを長く保持することになるため、受信の完了を待つループはユーザー空間に置いています。

## USB 切断とデバイスの寿命

USB が切断されると、機種側は機種のロックの下で利用可能状態を 0 にしてから、`px4_card_unregister()` でカードリーダーの登録を外します。  
登録の解除は、カードが使っていた電源の参照を戻し (切断後なのでハードウェアには触れません)、以後の操作がすべて `-ENODEV` になるようにします。  
開いたままの記述子は機種共通層の小さな管理オブジェクトだけを参照し続けるため、機種のオブジェクトは pcscd が記述子を閉じるのを待たずに解放できます。  
pcscd は USB の切断を udev から、カードの挿抜を IFD ハンドラーへの定期的な問い合わせから知るので、デバイスファイルは `poll()` に対応していません。

## 機種差

カードリーダーを登録する機種と条件は、Windows 版の `HasCardReader()` に合わせています。

| 系統 | 登録する条件 |
|---|---|
| PX4 系 | PX-Q3U4・PX-Q3PE4・PX-Q3PE5 は `dev_id` が 1 の側だけ、それ以外の機種はすべて |
| PXMLT 系 | PX-MLT8PE の3チューナー側 (`PXMLT8PE3`) を除くすべて |
| ISDB2056 系 (PX-M1UR ・PX-S1UR を含む) | すべて |
| ISDBT2071 系 (DTV03A-1TU) | すべて |

PX-Q3U4・PX-Q3PE4・PX-Q3PE5 と PX-MLT8PE は、1つの筐体が2つの USB デバイスとして見える機種で、カードスロットがあるのは片方だけです。  
カードスロットのない側でも pcscd は IFD ハンドラーを読み込みますが、カードリーダーは見つからないまま終わります (接続時に3秒ほどかかります)。

## 検証

リポジトリのルートから、カーネルモジュールと IFD ハンドラーをビルドして自動試験を実行します。

```bash
make -C driver
make -C pcsc
make -C pcsc check
```

### 実機に依存しない試験

`make -C pcsc check` は、次の3つを実行します。  
PID と GUID の照合には Python 3 が必要です。

- Windows 版と共有する T=1 の状態遷移の試験
- IFD ハンドラーの関数から `LinuxCardDevice` までを実物で通し、open・close・ioctl のシステムコールだけを模擬する試験 (未挿入、電源、T=1 、抜去、複数のカードリーダーの区別、コマンドを知らない古いカーネルモジュールなど)
- カーネル側の PID・GUID の表と Windows 版の INF の照合

実際の pcscd と libpcsclite を使う統合試験は、ホストの pcscd へ接続しないよう、試験専用のコンテナの中で実行します。  
USB デバイスとホストの PC/SC のソケットを渡さず、pcscd を起動していないコンテナの root で、次を実行します。

```bash
cd pcsc
make integration-build
PX4_ISOLATED_TEST=1 sh tests/run-pcsc-integration.sh
```

`libifd-px4-test.so` は模擬のカードを使う統合試験専用で、実際の環境へ配置するのは `libifd-px4.so` です。

### 実機試験

自動試験はカードとの実際の通信、TS 受信への影響、電源の遷移を確かめられないため、変更したときは実機で次を確認します。

- カードだけを使ったときのカードリーダーの列挙、ATR 、APDU
- チューナーとカードの同時使用 (どちらを先に閉じても他方が使い続けられること)
- 最後の利用者が閉じたときだけ基板の電源が切れること (`px4_backend_set_power` などの dynamic debug で遷移を見られる)
- 通信中の USB 切断と再接続、通信中のカードの抜去と再挿入
- 外付けのカードリーダーとの共存

同時使用の試験では、APDU の失敗数と最大処理時間に加えて、同期エラー、transport error 、continuity error 、空受信を記録します。

## 変更時の確認項目

- 機種を追加するときは、`struct px4_card_backend` を渡すだけで済み、ioctl の処理を機種側へ複製していないか
- 機種のチューナーを開く処理と閉じる処理が、カードの電源の参照を見て電源を入れ直したり切ったりしていないか
- 失敗の経路で、取得した電源の参照を戻しているか
- USB 切断時に、機種のロックの下で利用可能状態を 0 にしてから登録を外しているか
- `Info.plist` に機種を加えたとき、3つの配列の件数と並びがそろい、1行に1つずつ書かれているか
- 機種を加えたとき、`px4_card.c` の PID と GUID の表にも加えたか (`make -C pcsc check` が Windows 版の INF と照合する)
- `smart_card.cpp` を変えたときは、Windows 版のビルドと試験も通るか

## 採用しなかった構成

T=1 の状態機械をカーネルに置く構成は採用しませんでした。  
受信待ちと再送がカーネルのロックの下で長く続き、TS 受信と同じ USB ブリッジの制御を待たせるうえ、模擬の I/O で試験できないためです。

USB バス層 (`itedtv_bus`) にタスクごとの期限を持たせ、制御転送ごとに打ち切る構成も採用しませんでした。  
全機種の制御転送が通る共通部分に、カードのためだけの状態を持たせることになり、APDU 全体の期限は `smart_card.cpp` の検査で足りるためです。

検出のたびに電源の参照を取る構成と、カードを閉じるときにリセット線 (GPIO H14) を Low へ落とす構成も採用しませんでした。  
前者は pcscd の問い合わせで電源が切れなくなり、後者は Windows 版の `CloseCard()` にない操作で、必要とする理由も確認できていないためです。
