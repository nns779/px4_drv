# 2026年10月18日 公式 Windows ドライバー (PXQ3U4.sys) の解析記録

この文書は、PLEX が配布している PX-Q3U4 の公式 Windows ドライバーを静的に解析し、内蔵カードリーダーの扱いと、px4_drv との設計の違いを調べた記録です。  
目的は2つあり、PX-Q3 系のカードスロットの位置の判断材料を得ることと、px4_drv が公式ドライバーより安定している理由を、今後の変更で守るべき設計の原則として書き出すことです。  
Linux 版内蔵カードリーダー対応の確認の範囲は [実機確認の記録](20261014_linux_card_reader_validation.md) に、設計は [`pcsc/README.md`](../pcsc/README.md) にあります。

## 対象と方法

- 対象: PLEX の公式サイトの `pxq3u4_BDA_ver1x64.zip` に含まれる `PXQ3U4.sys` (版 17.07.27.1 、2017年7月) と `PXQ3U4.inf`
- 比較先: px4_drv の `3ce5eda` (Linux 版は `driver/` 、WinUSB 版は `winusb/src/DriverHost_PX4/`)
- 方法: コンテナの中の Ghidra と objdump による静的解析。ドライバーは実行・読み込み・インストールしていない

以下のアドレスは、ImageBase を `0x10000` とした仮想アドレスです。  
命令列から確かめた処理と、そこから推定した障害の経路を分けて書きます。推定した経路と、実際の BSOD やドロップとの因果関係は検証していません。

## 内蔵カードリーダー

### カードスロットの位置

公式ドライバーには、PX-Q3U4 の2つの USB デバイスのどちらか片側でだけカードを扱う分岐はありませんでした。  
`0x2C3C4` が USB デバイスごとの設定に `UART_Type=2` を固定で書き、`0x1FE30` がそれを反映し、`0x216AC` が UART のコマンド `0x37` に値 1 を送って B-CAS のモードにします。  
カードへの要求 (`0x15B34`) も要求を受けた USB デバイス自身を使い、シリアル番号の末尾の桁での選別や、相方への転送はありません。

このことは、両側にカードがつながっている証拠にはならず、公式ドライバーからはスロットの位置を判断できないことを意味します。  
px4_drv が PX-Q3 系でシリアル番号の末尾の桁が 1 の側にだけカードリーダーを登録している根拠は、PX-Q3U4 でその側の ACAS と通信できたという外部の報告です。  
INF が対象にしている PID は `004A` と `084A` だけで、PX-Q3PE4 (`024A`) と PX-Q3PE5 (`074A`) は含まれていません。  
`004A` は px4_drv が扱っていない PID です。

### カードの操作

カードの操作の基本の手順は、px4_drv と同じでした。

| 操作 | 公式ドライバーの処理 |
|---|---|
| 検出 (`0x1F988`) | GPIO6 を入力にして Low を検出する |
| リセット (`0x22E3C`) | GPIO14 を操作し、UART のコマンド `0x35` で速度を 9600bps に戻し、5ms 待つ。リセットの解除後は GPIO14 を入力に戻す |
| 送信 (`0x22C54`) | コマンド `0x34` で最大48バイトずつ送り、最後のブロックでレジスター `0x4965` に 1 を書く |
| 受信 (`0x24DFC`) | レジスター `0x496B` の長さを読み、コマンド `0x33` で受け取る。受信の完了はレジスター `0x496A` で判定する |

違いは、リセットの解除後の GPIO14 の扱いです。  
px4_drv と ITE の Linux 用のコードは GPIO14 を High の出力のまま保ちますが、公式ドライバーは入力に戻します。  
どちらが正しいかは、両側の USB デバイスでの実機の比較がないと判断できません。

### 基板の電源

公式ドライバーの電源の処理 (`0x2CAB0`) は、同じ USB デバイスの4チューナーだけを数え、px4_drv の `px4_mldev` にあたる、2つの USB デバイスの電源を連動させる管理はありません。  
電源を入れるときの待ちは、公式が GPIO7 と GPIO2 の操作の間に 500ms ・10ms ・10ms 、px4_drv が 80ms ・20ms です。

## BSOD の原因の候補

公式ドライバーには、カーネルのメモリを壊すおそれのある経路が3つありました。  
WinUSB 版 px4_drv はユーザー空間で動くので、同じ不具合があっても OS は止まりませんが、それとは別に、次の場面の作りそのものが違います。

- **転送の取り消しと解放の競合:** 公式ドライバーは、受信を止めるときに転送の要求 (IRP) を一覧から外してロックを解き (`0x1C26C`)、その後で取り消します (`0x1C29B`)。その間に完了の処理 (`0x1B913`) が同じ要求を解放できるので、止める側が解放済みの要求を取り消す順序 (解放後の参照) がありえます。WinUSB 版は、受信のスレッドの中で同期的に `WinUsb_AbortPipe` を呼び、スレッドの終了を待ってから転送のバッファを解放します
- **TS の処理の並列化:** 公式ドライバーは転送の完了ごとに作業項目を投入し (`0x1B718`)、その処理 (`0x1AF40`) が同期の位置・端数・書き込みの位置を排他なしで更新します。システムの作業項目は複数のスレッドで処理されうるので、同時に動けば状態が食い違います。処理中の作業の数も、投入した後に増やし、バッファを返す前に減らしているので、終了の判定に隙間があります。WinUSB 版は1本の受信のスレッドが受信した順に処理し、止める側はそのスレッドの終了を待ちます
- **同期を探すときの範囲外の参照:** 公式ドライバーの `0x1AE3C` は、`i < データの長さ` だけを確かめて `i + 188` と `i + 376` も読み、バッファの末尾の余白は 188 バイトしかありません。末尾の近くで同期を探すと、バッファの外を読みます。WinUSB 版の `StreamProcess` は残りの長さを確かめてから4パケットを検査し、足りない分を次の受信へ持ち越します

## ドロップ率の差の原因の候補

TS を捨てる単位と、処理の順序に違いがありました。

- 公式ドライバーは、長さが 188 バイトの倍数でない転送を丸ごと捨てます (`0x1B484`)。px4_drv は端数を保存して、次の受信とつなぎます
- 公式ドライバーは、アプリケーションへ渡すバッファが足りないと、816 パケット分をまとめて捨てます (`0x1AC20`)。px4_drv は、チューナーごとのリングバッファ (既定 2048 パケット) へ 188 バイトずつ書きます。バッファが満杯のときに失うのは、どちらも同じです
- 公式ドライバーは、完了のたびに作業領域を確保し、作業が残っていても転送を補充します。確保に失敗すると、受信した分を捨てます。WinUSB 版は開始時に確保したバッファを使い回し、整形・書き込み・次の転送の投入を1本のスレッドで順に行います

転送の大きさと数は、公式が 153,408 バイトを最大6本、WinUSB 版が 153,600 バイト (既定の RAW_IO で 512 バイト境界に丸めた長さ) を5本で、ほとんど同じです。  
公式ドライバーも次の転送は専用のスレッドが補充していて、作業項目の終わりを待つことによる遅れを主な原因とする根拠はありません。  
選局の処理 (`0x22438`) が下位の処理の失敗の後も成功を返す経路もあり、壊れた状態のまま受信を続ける原因の候補です。

## px4_drv の設計の原則

公式ドライバーとの比較で、px4_drv が安定している理由と考えられる作りを、今後の変更で確かめられる形でまとめます。  
受信した順の処理・停止の待ち・端数の保存は、原著者の初期の実装 (`a2213e9` ・`73a76f1`) から続く作りで、カードのための電源の参照は後年の追加です。

| 原則と確かめること | Linux 版 | WinUSB 版 |
|---|---|---|
| 転送を止めてから資源を回収する。取り消しや処理の終了より先に解放しない | `itedtv_bus.c` の `itedtv_usb_stop_streaming` | `itedtv_bus_winusb.c` の `itedtv_usb_stop_streaming` |
| バッファは開始時に確保して使い回す。受信のたびに確保せず、際限なく滞留させない | `itedtv_bus.c` の `itedtv_usb_alloc_urb_buffers` | `itedtv_bus_winusb.c` の `itedtv_usb_alloc_work_buffers` |
| 受信と制御の待ちを分ける。TS の処理の中でスリープ・カードの応答待ち・制御のロックの取得をしない | `itedtv_bus.c` の `itedtv_usb_complete` 、`it930x.c` の `it930x_ctrl_msg` | `itedtv_bus_winusb.c` の `itedtv_winusb_worker` 、共通の `it930x_ctrl_msg` |
| 有効な長さの中で同期を探し、端数を保存する。分割された受信や同期の崩れで、意図しない欠落や範囲外の参照をしない | `px4_device.c` の `px4_device_stream_process` と `px4_device_stream_handler` | `px4_device.cpp` の `StreamProcess` と `StreamHandler` |
| 制御の失敗は呼び出し元へ返す。選局や開始の失敗を成功に変えない | `px4_device.c` の `px4_chrdev_tune_t` と `px4_chrdev_tune_s` | `px4_device.cpp` の `Px4Receiver::SetFrequency` と `StartCapture` |
| 共有の電源は全利用者で判断する。カードだけ・相方だけが使っているときに停止しても給電を保つ | `px4_mldev.c` の `px4_mldev_set_power` と `px4_mldev_set_card_power` | `px4_device.cpp` の `MultiDevice::SetPower` と `SetCardPower` |

Linux 版内蔵カードリーダー対応をこの原則に照らした結果は、[実機確認の記録](20261014_linux_card_reader_validation.md) の「原著者の設計の原則との照合」にあります。
