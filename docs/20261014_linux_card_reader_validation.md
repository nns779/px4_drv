# 2026年10月14日 Linux 版内蔵カードリーダーの実機確認の記録

この文書は、Linux 版の内蔵カードリーダー対応 (`feature/linux-card-reader` ブランチ) を実機で確かめた結果と、確かめられていない機種・条件をまとめたものです。  
構成と取り決めは [Linux 版内蔵カードリーダーの設計資料](../pcsc/README.md) を参照してください。

## 検証環境

この記録の「WSL 検証環境」は、次の構成を指します。

- Windows 11 上の WSL2 (Ubuntu 24.04 、カーネル 6.18.54.1-microsoft-standard-WSL2)
- チューナーは Windows に USB 接続し、usbipd-win の USB/IP で WSL2 へ渡している
- pcsc-lite 2.0.3 (Ubuntu 24.04 のパッケージ) の pcscd を root で起動し、IFD ハンドラーはこのブランチからビルドして配置
- カードはいずれも内蔵スロットに挿した B-CAS で、ATR は `3b f0 12 00 ff 91 81 b1 7c 45 1f 03 99`
- アンテナは、PX-MLT5PE と DTV02A-1T1S-U には地上波と BS を、PX-W3U4 には地上波だけを接続
- pcsc-lite の版による違いは、同じ WSL2 に入れた Ubuntu 26.04 (pcsc-lite 2.4.1) で確かめた
- 古い pcsc-lite は、Ubuntu 20.04 (pcsc-lite 1.8.26) と Debian 12 (Mirakurun の公式イメージ、pcsc-lite 1.9.9) のコンテナで確かめた

USB/IP と仮想マシンを経由するため、TS のドロップ・同期エラー・連続性エラーは、ネイティブ Linux の結果として評価していません。  
TS の計数は、受信が止まらずに続くことの確認として扱っています。

APDU の試験には、pcscd 経由でカードへ B-CAS の初期設定コマンド (`90 30 00 00 00`) を繰り返し送り、`90 00` が返った数と処理時間を数えるツールを使いました。  
基板電源の遷移は、各機種の `*_backend_set_power()` の dynamic debug をカーネルログへ出して確かめています。

## 確認できたこと

この節の表と続く段落は f5082d7 までの変更 (デバイスファイルが `/dev/px4cardN` だった版) での結果です。

| 機種 | カードリーダーの列挙と APDU | チューナーとの同時使用と基板電源 | その他 |
|---|---|---|---|
| PX-MLT5PE | 200回成功 (平均 92.4ms 、最大 97.6ms) | 両方の順序で確認 | 通信中の USB 切断と再接続 |
| PX-W3U4 | 100回成功 (平均 92.6ms 、最大 100.2ms) | 両方の順序で確認 | |
| DTV02A-1T1S-U | 100回成功 (平均 82.6ms 、最大 87.6ms) | 両方の順序で確認 | PX-M1UR を統合した後の版でも受信と APDU を確認 |

同時使用の試験では、カードを先に開いてチューナーを開き、カードを先に閉じる順序と、チューナーを先に開いて先に閉じる順序の両方を確かめました。  
どの機種でも、APDU は失敗せず、受信も最後まで続きました。  
基板電源は最初の利用者が開いたときに1回だけ入り、最後の利用者が閉じたときに1回だけ切れました。  
pcscd がカードの有無を問い合わせているだけの待機中は、電源は入りませんでした。

PX-MLT5PE では、APDU を連続で送っている最中に usbipd-win で USB を切断しました。  
アプリケーションには `SCARD_E_READER_UNAVAILABLE` が返り、`/dev/px4card0` は消え、カーネルログに警告や oops は出ませんでした。  
再接続すると `/dev/px4card0` が作り直され、APDU 50回がすべて成功しました。

PX-MLT5PE・PX-W3U4・DTV02A-1T1S-U の3台を同時に接続すると、3つのカードリーダーがそれぞれ別のリーダーとして列挙されました。

### DTV02A-1T1S-U の受信開始直後のエラーについて

DTV02A-1T1S-U で、カードへ APDU を送っている最中にチューナーを開いた1回の試験で、受信開始から 1.15〜1.22 秒の間に transport error indicator が25件、連続性エラーが4件出ました。  
カードの状態 (使っていない・電源だけ入れている・通信中) を変えて受信開始直後の8秒を4回ずつ、計12回繰り返したところ、すべて0件で再現しませんでした。  
カードの状態との関係は見られなかったため、カード対応による変化とは判断していませんが、原因は確かめられていません。

### /dev/px4card の下に作る形と deb での確認

デバイスファイルを `/dev/px4card/` の下に作る形にした版と、`build_pcsc_deb.sh` で作った deb の IFD ハンドラーで、上と同じ3台を確かめ直しました。  
この時点のデバイスファイル名は USB のシリアル番号で、現在の ID の名前は後の「Windows 版と同じ ID の名前」の節で確かめています。

- 3台とも `/dev/px4card/` の下に作られ、権限は udev の規則どおり `root:video` の `0660` だった
- pcscd には `PLEX PX-MLT5PE Smart Card Reader (000042546005001) 00 00` のような名前で列挙され、3台へ同時に APDU を100回ずつ送り、すべて成功した
- PX-MLT5PE を APDU の送信中に切断すると、そのデバイスファイルだけが消え、再接続すると同じ名前で作り直された。再接続後の APDU 50回はすべて成功し、カーネルログに警告や oops は出なかった

### PX-M1UR

PX-M1UR を単独で接続し、カードを挿していない状態と、Mini B-CAS を挿した状態の両方を確かめました。

- カードなしでは、`pcsc_scan` がカードなし (Card removed) と表示し、アプリケーションからの接続には `SCARD_E_NO_SMARTCARD` (No smart card inserted) が返った
- カードありでは、ATR は `3b f0 12 00 ff 91 81 b1 7c 45 1f 03 99` で、単独の APDU 100回がすべて成功した (平均 87.0ms 、最大 93.6ms)
- チューナーとの同時使用は、カードを先に開いて地上波 27ch を受信する順序と、BS15_0 の受信を先に始めてカードを開く順序の両方で、APDU (200回と400回) がすべて成功し、受信の同期ずれ・TEI・連続性エラーは0件だった
- 基板電源は、どちらの順序でも最初の利用者が開いたときに1回だけ入り、最後の利用者が閉じたときに1回だけ切れた
- カードなしの状態でも、地上波 27ch と BS15_0 をそれぞれ20秒受信し、同期ずれ・TEI・連続性エラーはすべて0件だった

### 通信中のカードの抜去と再挿入

PX-M1UR で APDU を送り続けている最中に、Mini B-CAS を手で抜き、約5秒後に挿し直しました。

- 抜いた時点で送信中の APDU は失敗し、同じ接続のその後の APDU には `SCARD_W_REMOVED_CARD` (Card was removed) がすぐ (平均 9ms) 返った。応答を待ち続けて止まることはなかった
- `pcsc_scan` は、カードあり・カードなし・カードありの遷移を表示した
- 挿し直した後は、新しい接続で同じ ATR を取得し、APDU 50回がすべて成功した
- 接続を作り直しながら APDU を送り続ける形でも、2回の抜き差しのどちらの後も、挿し直した直後の接続から APDU が成功した
- カーネルログに警告や oops は出なかった

抜く前の接続には、挿し直した後も `SCARD_W_REMOVED_CARD` が返り続けます。  
これは PC/SC の取り決めどおりの動作で、アプリケーションは `SCardReconnect()` などで接続し直す必要があります。

### 受信とカード通信の同時実行

DKMS でインストールした同じ版で、全チューナーの受信と、3台のカードへの APDU の送信を同時に行いました。  
APDU は受信開始の3秒後から、3台へそれぞれ連続で送り続けています。

| 試験 | 受信したチューナー | 同期ずれ・TEI | 連続性エラー | APDU |
|---|---|---|---|---|
| 地上波 27ch 、120秒 | PX-MLT5PE の5基、PX-W3U4 の地上波2基、DTV02A-1T1S-U | すべて0件 | PX-MLT5PE のチューナー3で1件 | 3台とも896回成功 |
| BS15_0 、60秒 | PX-MLT5PE の5基、DTV02A-1T1S-U | すべて0件 | PX-MLT5PE のチューナー0・3・4で各1件 | 3台とも416回成功 |

連続性エラーは、いずれも受信開始から 1.8〜2.2 秒の時点に PID 256 で1件ずつ出たもので、APDU を送り始める前でした。  
カード対応の前の版でも、受信開始の約 1.7 秒後に同じ PID で1件出ることがあり、同じ傾向と見ています。  
最大読み出し間隔は、PX-MLT5PE のチューナー0の地上波の 0.234 秒を除いて 0.07 秒以下でした。

PX-W3U4 の衛星側の2基は、同軸ケーブルを衛星側につなぎ替えたうえで、デバイスファイル名を ID にした版で確かめました。  
受信しながら、PX-W3U4 ・PX-M1UR ・DTV02A-1T1S-U の3台のカードへ APDU を送り続けています。

| 試験 | 受信したチューナー | 同期ずれ・TEI | 連続性エラー | APDU |
|---|---|---|---|---|
| BS15_0 、60秒 | PX-W3U4 の衛星側2基 (C/N 17.9dB 、17.7dB) | すべて0件 | 0件 | 3台とも416回成功 |
| CS2 、30秒 | PX-W3U4 の衛星側2基 (C/N 16.7dB 、17.3dB) | すべて0件 | 0件 | 3台とも176回成功 |

### pcsc-lite の版とデバイスファイルの権限

pcsc-lite 2.4 以降は、systemd の下の pcscd が root ではなく `pcscd` ユーザーで動きます。  
Ubuntu 26.04 (pcsc-lite 2.4.1) の WSL を用意し、PX-M1UR を接続して、udev の規則のカードリーダーの行だけを変えて比べました。

| 環境 | pcscd の実行ユーザー | デバイスファイルの権限 | 結果 |
|---|---|---|---|
| Ubuntu 26.04 | `pcscd` | `root:video` の `0660` | pcscd が開けず、`init failed` でカードリーダーが一覧に出ない |
| Ubuntu 26.04 | `pcscd` | `root:pcscd` の `0660` | 一覧に出て、APDU 20回成功 |
| Ubuntu 24.04 | root | `pcscd` グループの規則 (グループは存在しない) | 一覧に出て、APDU 20回成功 |

Ubuntu 24.04 では `pcscd` グループが存在しないため、udev はグループの指定を無視します。  
デバイスファイルのグループは変わらずに残りますが、root で動く pcscd はそのまま開けます。

配布する deb は、CI と同じく Ubuntu 20.04 のコンテナで作り、Depends は `libc6 (>= 2.17)` になりました。  
同じ Ubuntu 20.04 のコンテナの pcscd (pcsc-lite 1.8.26) にこの deb を読み込ませると、PX-M1UR を認識し、APDU 20回がすべて成功しました。  
開けなかったときのログのために pcscd の関数を使っていますが、この版でも読み込みのエラーは出ていません。

### 外付けのカードリーダーとの併用

外付けのカードリーダー (SCM Microsystems SCR3310 、libccid 1.5.5 で動作) と、PX-W3U4 ・PX-M1UR ・DTV02A-1T1S-U の内蔵カードリーダーを、同じ pcscd に同時に接続しました。  
4台はそれぞれ別のリーダーとして列挙され (外付けのリーダーが先頭)、4台へ同時に APDU を100回ずつ送り、すべて成功しました。

### root 以外のサービスから使う場合

Ubuntu 24.04 の pcscd は、polkit の既定でログインしていないユーザーからの接続を拒否します。  
`video` グループに入った一般ユーザーを systemd のサービスとして動かすと、`SCardEstablishContext` が `Access denied` になり、pcscd のログに `is NOT authorized for action: access_pcsc` が出ました。  
README に載せた polkit の規則でそのユーザーを許可すると、同じサービスから APDU 10回がすべて成功し、規則を外すと再び拒否されました。

### Docker のコンテナで使う場合

ホストの pcscd を止め、Mirakurun の公式イメージ (`chinachu/mirakurun:latest` 、Debian 12 、pcsc-lite 1.9.9) に、CI と同じ Ubuntu 20.04 のコンテナで作った deb を追加したイメージで確かめました。  
起動の設定は公式の `docker-compose.yml` と同じく、`/dev:/dev` の volume 、host ネットワーク、`c *:* rmw` の `device_cgroup_rules` です。

- Mirakurun の起動処理が動かす pcscd が PX-M1UR を認識し、APDU 20回がすべて成功した
- PX-M1UR を抜き差しすると、作り直された `/dev/px4card/8E5C59AEFF108DEA` がコンテナからもそのまま見え、APDU が成功した
- ホストの pcscd (pcsc-lite 2.0.3) を使い、コンテナでは `DISABLE_PCSCD=1` を設定して `/var/run/pcscd` を渡す構成でも、コンテナの中の `pcsc_scan` にカードリーダーが表示された

最後の機器を外すと、カーネル (devtmpfs) は空になった `/dev/px4card` を削除します。  
`/dev/px4card` だけをコンテナへ渡していると、作り直されたディレクトリがコンテナから見えなくなるため、`/dev` 全体をマウントする構成を前提にしています。

### Windows 版と同じ ID の名前

デバイスファイル名を Windows 版のリーダー名の ID にした版を DKMS でインストールし、3台を同時に接続して確かめました。  
ID は、同じ機器の Windows 版のリーダー名に表示された値と一致しました (PX-M1UR は、TVTest の設定画面で見えた先頭4桁の `8E5C` までを照合)。

| 機種 | USB のシリアル番号 | デバイスファイル | Windows 版のリーダー名の ID |
|---|---|---|---|
| PX-M1UR | `000000000000001` | `/dev/px4card/8E5C59AEFF108DEA` | `8E5C59AEFF108DEA` |
| PX-W3U4 | `000001711009061` | `/dev/px4card/CD65353E4231AA77` | `CD65353E4231AA77` |
| PX-MLT5PE | `000042546005001` | `/dev/px4card/E0044EBBED627D79` | `E0044EBBED627D79` |
| DTV02A-1T1S-U | `000000000000001` | `/dev/px4card/3D5490589EDEA2B5` | (Windows 版の表示とは未照合) |

PX-M1UR ・PX-W3U4 ・PX-MLT5PE の3台は、pcscd に列挙され、APDU 10回ずつがすべて成功しました。  
DTV02A-1T1S-U は、PX-W3U4 の衛星側の試験と同時に接続し、Windows 版と同じ式で計算した値の名前で作られることを確かめました。

PX-M1UR と DTV02A-1T1S-U はどちらもシリアル番号が `000000000000001` ですが、PID と GUID が異なるため、ID は別の値になります。  
同じ機種でシリアル番号も同じ機器を複数台つないだ場合は ID も同じになり、2台目以降のデバイスファイル名には接続した順に `-1` などが付きます。  
手元に同じ機種が1台ずつしかないため、この場合と、シリアル番号を持たない機器の `usb-<USB の接続位置>` の名前は確かめられていません。

### pcscd のリーダー名の ID

px4_drv が USB インターフェースの `interface` 属性で `ID: <ID>` を返すようにした版で、PX-MLT5PE ・PX-W3U4 ・DTV02A-1T1S-U ・PX-M1UR の4台を接続して確かめました。

```text
PLEX PX-MLT5PE Smart Card Reader [ID: E0044EBBED627D79] (000042546005001) 00 00
PLEX PX-W3U4 Smart Card Reader [ID: CD65353E4231AA77] (000001711009061) 01 00
e-Better DTV02A-1T1S-U Smart Card Reader [ID: 3D5490589EDEA2B5] (000000000000001) 02 00
PLEX PX-M1UR Smart Card Reader [ID: 8E5C59AEFF108DEA] (000000000000001) 03 00
```

4台とも、リーダー名の `[ID: ...]` がデバイスファイル名と同じ値になりました。  
pcscd は USB が追加されたという通知を受けて名前を作るため、通知と属性の作成が競合しないかも確かめました。  
pcscd を動かしたまま PX-M1UR を5回抜き差しすると、5回とも ID 付きの名前で追加されました。  
モジュールを外すと `interface` 属性は4台ともすべて消え、カーネルのログに警告は出ませんでした。

### px4card クラスと作り直した ioctl

カードリーダーを専用の `px4card` クラスで登録し、ioctl を `CardDevice` と1対1のコマンドに作り直した版を DKMS でインストールし、IFD ハンドラーも同じ版に入れ替えて、PX-M1UR ・PX-W3U4 ・PX-MLT5PE ・DTV02A-1T1S-U の4台で確かめました。

- 4台とも、sysfs は `/sys/class/px4card/<ID>` 、デバイスファイルは `/dev/px4card/<ID>` 、udev の `DEVNAME` も同じ名前になり、`SUBSYSTEM=="px4card"` の規則で権限が `0660` になった (この環境には `pcscd` グループがないため、グループは `root`)
- pcscd のリーダー名は前の節と同じく ID 付きで列挙され、4台へ APDU を20回ずつ送り、すべて成功した
- pcscd を動かしたまま PX-M1UR を抜き差しすると、その項目だけが sysfs ・デバイスファイル・pcscd の一覧から消え、再接続すると同じ名前で作り直されて APDU 20回がすべて成功した
- PX-W3U4 の衛星側の2基で BS15_0 を60秒、CS2 を30秒受信しながら、PX-W3U4 ・PX-M1UR ・DTV02A-1T1S-U へ APDU を送り続けた。受信は4回とも同期エラー・transport error indicator・連続性エラーが0件で、APDU は BS の間に416回ずつ、CS の間に176回ずつ、すべて成功した
- モジュールを外すと `/sys/class/px4card` 、デバイス番号、`/dev/px4card` がすべて消え、読み込み直すと4台とも同じ名前で作り直された。カーネルのログに警告や oops は出なかった

カーネルモジュールは、Ubuntu 20.04 の標準カーネル (5.4.0-216-generic) のヘッダーでも、警告なしにビルドできました。  
Ubuntu 18.04 の 4.15 は develop の `px4_usb.c` の `fallthrough` でビルドに失敗し、このブランチで追加したコードとは関係ありません。  
その後、`fallthrough` が未定義のときだけ互換の定義を置き、Ubuntu 18.04 (4.15.0-213-generic) でも警告なしにビルドできるようになりました。

### root 以外の pcscd での接続直後の権限

登録の直後のデバイスファイルは `root` の `0600` で、udev が `pcscd` グループの `0660` に直すまでの間は、root 以外の pcscd が開けません。  
以前の IFD ハンドラーはこの間の `EACCES` で登録を打ち切っていたため、期限まで再試行するように直し、Ubuntu 26.04 (pcsc-lite 2.4.1 、pcscd は `pcscd` ユーザーで動作) で確かめました。

- pcscd を動かしたまま PX-M1UR の切断と再接続を4回繰り返し、毎回 ID 付きの名前で登録し直された。デバイスファイルを開けなかった記録は1件もなく、最後の APDU 20回はすべて成功した
- open でデバイス番号に加えて cdev も照合するように直した版でも、4台の名前と APDU 20回ずつ、PX-M1UR の抜き差し後の APDU を確かめた

pcscd が px4_drv のモジュールより先に USB を列挙すると、リーダー名に `[ID: ...]` が入りません。  
カーネルは USB の追加を通知してから probe を呼ぶため、この順序はカーネル側では防げず、pcscd を起動し直すと ID の入った名前になります。

### 実機のない機種のコードによる確認

手元に実機がない機種は、コードを追い、電源管理などの関数を実際にコンパイルして USB の操作を模擬する試験で確かめました。  
これはコードの上での確認で、実機での受信やカードの通信を確かめたものではありません。

- PX-Q3U4・PX-Q3PE4・PX-Q3PE5 の2基連動の電源管理を、すべての連動モードで開閉の順序を変えながら約3万9千通り試し、カード・自分の側のチューナー・相方のチューナーのどれかが使っている間は電源が保たれた。カードを使わない約2万通りでは、電源を操作する順序と回数が develop と同じだった
- 機種ごとのカードリーダーの登録先 (PX-Q3 系はシリアル番号の末尾の桁が 1 の側、PX-MLT8PE は5チューナー側) と、PID・GUID・I2C アドレス・入力ポートが、Windows 版と INF に一致した
- ISDB2056N ・PX-S1UR ・DTV03A-1TU は、受信・電源・切断の処理が旧版と効果の上で同じで、PX-S1UR の旧版との違いは意図した2点 (open 時の地デジ復調器のスリープ、衛星側の復調器への初期値の書き込み) だけだった

PX-Q3 系のカードスロットを片側に限る判定の根拠は、PX-Q3U4 でその側の ACAS と通信できたという外部の報告です。  
公式の Windows 用ドライバー (PXQ3U4.sys) を解析すると、両側の USB デバイスでカードを初期化していて、判定の手がかりにはなりませんでした。  
この INF は PX-Q3U4 の PID だけを対象にしていて、PX-Q3PE4 と PX-Q3PE5 の配線は分かっていません。

### 原著者の設計の原則との照合

公式の Windows 用ドライバーとの比較で、px4_drv が安定している理由として次の作りが確かめられました (解析の詳細は [公式 Windows ドライバーの解析記録](20261018_official_windows_driver_analysis.md))。

- 転送を止めてから資源を回収し、取り消しや処理の終了より先に解放しない
- バッファは開始時に確保して使い回し、受信のたびに確保しない
- 受信と制御の待ちを分け、TS の処理の中でカードの応答や制御のロックを待たない
- 同期を有効な長さの中で探し、端数を捨てずに次の受信とつなぐ
- 制御の失敗は成功に変えずに呼び出し元へ返す

内蔵カードリーダーの追加をこれらと照らし合わせたところ、守られていなかったのは、カードの層の初期化の失敗でモジュール全体の読み込みが失敗する1件で、チューナーは使えるように直しました。  
カードの UART の操作は機種のロックを持つため、その間はチューナーの開閉と選局が待たされますが、TS の受信の経路は待たされません。

## 確かめられていないこと

- 手元に実機がない機種
  - PX4 系: PX-Q3U4・PX-Q3PE4・PX-Q3PE5 (2基連動の電源管理を含む)、PX-W3PE4・PX-W3PE5
  - PXMLT 系: PX-MLT5U・PX-MLT8PE・DTV02A-4TS-P (DTV02A-5TS-P は PX-MLT5PE のリブランド品で、ハードウェアと通る処理が同じなので、PX-MLT5PE の結果に含めている)
  - ISDB2056 系: ISDB2056N・PX-S1UR
  - ISDBT2071 系: DTV03A-1TU
- PX-M1UR 以外の機種での、通信中のカードの抜去と再挿入
- ACAS チップ
- PX-W3U4 以外の機種での CS の受信、長時間の録画、ネイティブ Linux での TS の品質
- PX-Q3PE4 ・PX-Q3PE5 のカードスロットの位置

## 既存の問題

次の問題は、内蔵カードリーダー対応の確認の途中で見つかったもので、develop の時点からあります。  
どれも録画にかかわる経路なので、この対応とは分けて、実機で確かめてから直します。

- PX-Q3 系で最初のチューナーを開いたとき、相方の電源の投入だけが失敗すると、使用中の記録が残り、次に開くときに必要な初期化が省かれる (`px4_mldev.c`)
- ISDB2056 系と ISDBT2071 系で、同期の確認に必要な4パケットに満たない受信を、端数として残さずに捨てる (`isdb2056_device.c` ・`isdbt2071_device.c`)。1回の USB 転送は大きいので、転送が極端に短く切れたときだけ起きる
- WinUSB 版の `Px4Device::Term()` は、受信の停止を待つ前にストリームの参照を外していて、受信の処理が残っていると空の参照を使う順序がありうる (原著者の実装から同じ順序で、落ちたという報告はない)
- WinUSB 版のカードリーダーのサーバーは、終了時に内部のデータを破棄してから接続の受け付けを止めるので、その間に届いた接続が破棄済みのデータに触れる順序がありうる
